## 目标:

* 开发一套"开发系统", 包含设计, 开发, 质量, 文档等一套流程. 能够充分约束AI agent, 让它产出稳定的代码.
* 期望这个应用是面向企业级的, 因此最重要的目标是保证开发质量.
* 支持多用户, 可以团队开发一个大型项目.（现状：已有账号、JWT、负责人、任务分配、工作量和操作留痕。TODO：项目成员、项目隔离及更细的权限控制。）
* 对于AI模型: 能够适配不同能力的AI. 因为未来对接的模型会包括从GPT 5.5到Qwen3.6 27B这样不同级别的模型.（现状：支持角色模型配置，已有行为评测脚手架。TODO：跨模型、跨领域验证流程遵守情况、稳定性、成本和上下文消耗。）
* 整体流程可以总结为: 需求意图 → 工程约束 → AI 生产 → 质量验证 → 组织沉淀

## AI agent的优缺点

优点
1. 生成代码非常快,
2. 代码质量非常高. 具体细节非常出色
3. AI追查问题很厉害, 定位很快.
4. 最擅长的事情是: 给它一个需求, 描述清楚, 让它自由发挥, 可以做的非常好. 比如各种js游戏.

缺点
1. 不知道隐含条件, 比如, 你让它估算$1111/1110$, 它肯定想尽办法做算数, 但是人类会考虑到, 我只要整数精度, 所以只要约等于1的结果就行. 如果把这个问题放大, 会导致设计出来的系统局部很精美, 甚至某些方面极为优秀, 但整体很低效.
2. AI擅长针对特定任务即兴发挥. 让它做个小游戏很好, 但是不擅长在大量约束下解决问题. 这恰恰是做工程需要的
3. 实际项目中, 不可能指望一个超人完成开发, 用AI也是一样, AI能力有限, 项目规模扩大, 也无法完成. 要把软件工程的方法用过来. 包括开发流程, 人员分工
4. 到了"类"往上的层级, 设计能力就下降了. 主要原因是, 他以为的需求和实际需求的矛盾.
5. AI很难确认歧义, 比如对于key, 在数据库领域和在crypto领域含义是不同的. 如果开发crypto带有数据库的系统, AI就容易犯错.
6. 语义漂移/不规范: 一个词在多次讨论/记录后, 会改变含义, 如照片管理中, 一开始把照片称为资产, 照片目录称为资产账本, 后面会把资产账本翻译成财务意义上的账本(ledger). 有时候还会用混用不同领域的含义. 比如把某某集合称为某某桶
7. 不会挖掘问题, 让他挖掘需求的时候, 很难针对现有要求, 提出问题.

如果要分析原因:
1. 对于AI agent来说, 长上下文的情况下, 注意力分散, 因此要减少每个小任务的上下文.
2. 如果约束太多太复杂, 即使上下文不够大, 也会会忘掉一些约束. 比如, 之前项目的经验: 给了一个非常细致的设计文档, 写出的代码还是会漏我已经要求的细节.



## 设计

### 总体思路

1. 总体的业务流是~~需求->设计->开发->review->测试~~（现状：INPUT → 项目宪法 → FEATURE → DESIGN → TASK → 开发与 qa → PR 与合并记录 → Integration → System；qa 同时承担测试和评审）。
2. 整体分为两大部分, 一块是~~需求->设计->任务~~（现状：INPUT → 项目宪法 → FEATURE → DESIGN → TASK）, 另一块是~~任务->开发->review->测试~~（现状：任务认领与适用的预审 → coder 开发 → qa 独立测试和评审 → manager 裁决 → PR 与合并记录）. 当然两部分是可以串联起来的. ~~一个任务需要能够知道对应了哪些设计~~（现状：设计来源的任务严格按一个 DESIGN 对应一个 TASK；变更来源的任务可以关联一个或多个已批准的 CR，不要求新建 DESIGN）, ~~一个需求也可以查询到分成了哪些任务. *需求和任务是多对多的关系*~~（现状：没有直接的 INPUT–TASK 多对多关系；设计通过需求摘录和引用表达来源，任务通过 DESIGN 或 CR 追溯其依据）。

任务要有依赖关系, 而且任务要设计好测试用例,(可以用DAG来管理任务依赖)

**开发部分**

这部分包含: 开发, 单元测试

开发过程要遵循以人为中心, 程序员申领任务. 然后fork一个分支开发. 开发完成后提交一个pull request, ~~系统会review~~（已删除：评审由独立的 qa agent 执行，manager 根据评审证据裁决，Harnoq 记录结果并检查门禁）. 通过reivew, 并运行完所有test, ~~就执行merge~~（已删除：不由 Harnoq 自动合并；人在代码托管平台确认合并后，由 agent 向 Harnoq 上报合并事实）. ~~这个流程可以用Github的CI实现, 系统只要生成项目配置并导入即可~~（已删除：Harnoq 不生成或集成 CI/CD 配置，测试由 agent 执行，CI/CD 由团队自行管理）.

本系统不限制程序员怎么开发, 用notepad手写都可以, 但是为了统一开发流程, 系统会提供一套统一的opencode/claude模板. 包括:

* 任务描述: 要做什么, 为什么要这么做, 为什么这么设计, 怎么写test.
* 去哪看文档/项目资料
* 开发过程分几个subagents, 以及它们如何分工
* 如何执行开发流程(通过文档告诉AI agent: ~~fork, research, coding, review, test, pull request~~（现状：manager 创建或复用任务分支，完成适用的预审后执行 research → coding → qa → pull request；qa 同时测试和评审，失败则修改后再次验证）)
* 需要用的skills

**重要**: 程序员拿到需求后, 需要review需求, 并与AI agent讨论开发方案, 如果发现需求不合理, 可以将需求打回. 在开发过程中, 要监督AI agent的开发过程, 如果有异常也要及时介入.



**集成测试**/系统测试

所有开发完成后, 进入集成测试和系统测试阶段. 在这里, 通过和主AI聊天, ~~生成测试任务~~（现状：先形成 INTEG / SYS 交付清单，在执行轮次中直接记录验证证据）. 程序员需要保证~~测试任务~~（现状：交付清单及其验证证据）的完善程度和覆盖率.

~~然后生成任务~~（现状：按清单安排验证工作，复用已有测试和环境，需要时补充；不为每项验证单独生成 TASK）:

1. ~~开发测试用例~~（现状：先检查已有用例能否证明清单义务，按缺口补充可执行验证，并记录命令、结果和代码版本）。
2. ~~开发mock环境和mock数据~~（现状：按验证需要复用或准备环境和数据，明确真实依赖与 mock 的边界，不统一要求新建 mock 任务）。

~~当测试用例和mock准备完善之后, 执行集成测试~~（现状：Integration 验证装配、跨设计接缝和重复实现，完成后进入 System 验证用户旅程及非功能要求；普通修复留在当前执行轮次，设计或契约变更进入 CR 流程）。

针对有web的项目, 在系统测试阶段, 还可以通过playwright或者Selenium进行web页面的测试.



**需求增加/bug修复**

系统上线后, 会有这两种情况, ~~流程也是, 先跟AI聊, 生成任务. 然后程序员申请任务, 并开发~~（现状：已交付功能的新增需求或变更先通过 CR 分析和批准，再创建或复用变更来源的 TASK，完成开发、qa 和 PR 流程；重新打开已完成任务用于修复有明确依据的原验收未满足问题。Integration / System 中不改变既定设计或契约的普通修复留在当前执行轮次，不要求 CR）。



> *重要*: 这段引用中包含的是一些想法, 不作为本系统需要实现的内容:
>
> 另一种思路是, 既然设计好了, 就放手让交给AI开发. 这样可以做的很fancy, 比如, 所有的AI model统一管理, 作为资源池. 配置好每个model的属性(比如gpt管code, GLM管test, opus管review). 然后把任务再打散成task.step(也就是dev/review/test), 再判定依赖关系(这个依赖关系要用图数据库管理), 让一个统一的调度器, 根据任务的依赖关系和model的空闲程度, 自动把step发送给model做. 具体来说: 如果model空闲, 调度器就会塞给他一个step, 做完了, 调度器根据依赖看看有没有可做的, 再塞给他一个step. 还可以设置看门狗, 以应对死循环(比如一个任务被review打回去超过10次).
>
> 这样全自动适合个人开发, 也适合无人值守跑完项目. 但是, 缺少人类交互的过程, 如果任务有问题, 就无法及时发现并改正. 本系统目标是生产面向商用的代码, 这样不可控的开发过程, 会造成代码质量不可靠.



代码管理用Github, 不管是自己部署的, 还是Github.com, ~~只要能对接就行~~（已删除：Harnoq 不直接连接代码托管平台，仓库操作由 agent 使用 git / gh / tea 等工具完成）, 另外这里的github会用本地的简化版: Gitea. 有了Github, 可以借助它做CI/CD, ~~我们的系统, 也要有跟Github对接的接口~~（已删除：不实现 GitHub / Gitea API 客户端，不轮询 PR 或 CI；Harnoq 只记录上报的 PR 与合并事实，避免重复适配各类托管平台）.
