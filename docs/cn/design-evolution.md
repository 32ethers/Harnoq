# Harnoq 设计演进与依据

[中文](design-evolution.md) · [English](../en/design-evolution.md)

> Harnoq 的设计是在持续开发和试用中逐步形成的。早期方案在实践中暴露出问题，促使我们不断调整，有些选择也经历过反复。本文记录这些探索与取舍，保留每次重要调整的背景和原因，帮助读者理解系统如何演变至今，以及当前设计为何如此。

Harnoq 最初希望把需求、设计、任务、开发和质量验证连成一套受约束的 AI 开发流程。实现和试用逐渐暴露出两个问题：流程层次多，不一定增加有效判断；模块任务各自通过，也不一定意味着整个产品可交付。后续调整围绕这两点展开：去掉没有独立职责的中间层，把真正缺失的设计决策、变更判断和全局验证补到明确的位置。

## 1. 起点：系统应当约束 AI 到什么程度

### 从完整开发流程出发

[初步设计](initial_design.md)关注的不是单次代码生成，而是 AI 在大型工程中的约束遵守：局部实现可以很好，却可能遗漏隐含条件、跨模块约定和质量要求。随着上下文变长、角色增多，仅靠一次对话交代全部要求并不可靠。因此最初就提出保存需求和设计、拆分任务、独立检查质量，并让人能够介入。

早期比较过以现有 PM/ALM 产品为底座，也讨论过把模型作为资源池、自动调度步骤的无人值守形态。当时继续自研的判断是：AI 辅助降低了 CRUD 和状态机的实现成本，值得用这些成本换取对数据模型、阶段方法和上下文粒度的控制；调研主要用于借鉴成熟的需求与变更模型，并未证明其他产品普遍不能胜任。无人值守形态在初步设计中就是未采纳的设想，不能当成后来删掉的已实现功能。Harnoq 继续自研，并保留人的任务选择、设计确认、适用的开发前评审和交付接受。

### 把工程记录与实际执行分开

早期方案还包含由 Harnoq 对接代码托管平台、检查 PR/CI 和自动推进合并。后来这部分职责收缩：仓库操作由 agent 使用相应客户端完成，Harnoq 保存设计、工作状态、证据和上报的 PR/合并事实。各类托管平台已有工具，再维护一套平台客户端会扩大系统边界；自动化执行也不能替代产品与设计判断。

由此形成当前分工：人决定目标与取舍，agent 执行设计和开发工作，Harnoq 保存可追溯记录并检查可机械判定的条件。系统能拒绝不合法的状态流转，但不能凭一条批准记录证明真实的人类同意，也不能凭一份测试报告证明代码必然正确。后面的简化和补充都在这一边界内进行。

## 2. 流程简化：每一层是否有独立职责

### 需求条目经历了删除、恢复和再次删除

早期在原始材料与设计之间设置 RequirementItem，把自由文本归一化为结构化需求条目。它曾合并回 SourceRequirement，后来又为追溯和变更管理恢复，最终再次删除。这个反复说明，需求分析的价值与“必须有一个独立需求实体”不是同一个判断。

独立 REQ 层增加了提问、填字段、确认和覆盖检查，却仍不能可靠发现隐含条件。提前固定原子条目还可能让功能边界围绕条目展开，而不是围绕真正需要封装的决定展开。最后保留 INPUT 作为整体原始材料，把详细需求与具体方案一起放入 DESIGN，让人根据可检查的设计发现遗漏和冲突。

这项选择减少了重复确认，但也明确放弃了独立原子需求层的完整关系矩阵。Feature 不直接绑定 INPUT，设计通过需求摘录和引用表达依据；不能把这种语义联系描述成数据库已经强制保证了逐项需求覆盖。

这个过程有两个不能省略的中间决定。第一次取消 REQ 时，原覆盖关系一度改挂 INPUT；恢复 REQ 时，则把原子条目放到 Feature 下面，用一个设计覆盖多个条目且不交叉，以便逐项追溯和分析变更。因此前后两次 REQ 的位置与目的并不完全相同，不能只记成“结构化字段没用”。最终删除发生在反复强化提问规则之后：按维度检查空白有效，主动提出无人提过的问题仍不稳定；先出具体草稿、让人指出错处才带来明显改善。

INPUT 的确认门也曾反转。早期 INPUT 只保留自由文本、不设确认；结果只要创建一份材料，阶段就跳到项目规范，需求澄清最多得到一次交互。于是补回确认门，要求所有有效 INPUT 确认后再推进，但没有把原来的结构化字段清单搬回来。这保留的是“原始材料已被澄清并认可”的停顿，不是恢复 REQ 实体。

### 任务计划与任务草案分两次退出

早期的任务创建经过设计、任务计划、任务草案，再生成正式任务。当时检查的 12 个 TaskPlan 的拆分策略全部为空，11 个只有一个草案；计划与设计严格一对一，单独审批没有增加独立决策，因此先把它的职责并入 DesignCase。此时 TaskDraft 仍在，草案及依赖直接挂到设计下。

随后发现，默认一个设计对应一个任务时，TaskDraft 仍然只是正式任务的字段副本。“生成任务”主要是在复制内容，却引入生成前后两套编辑规则。因此第二步删除 TaskDraft，直接从已确认设计创建可领取任务，并把任务定义的锁定时点从生成移到领取。

两步调整接受的代价也不同：删 PLAN 时把“批准设计”和“批准拆分”两道门合为设计确认，但生成仍限于人操作；删 DRAFT 时进一步取消仅人可生成任务的限制，让 agent 也能直接创建任务。人的设计确认与适用预审仍保留，不再用一次字段复制来承载额外批准。

```text
早期：        DESIGN → TaskPlan → TaskDraft → TASK
删除计划层后：DESIGN → TaskDraft → TASK
当前：        已确认 DESIGN → TASK（claimable，领取后锁定定义）
```

这里始终保留 DESIGN。代码中的 `DesignCase` 和 `design_case_service.py` 就是当前设计记录及其服务；它们承担设计编辑、确认和直接创建任务，不是被删除的计划或草案层。

早期还允许上下文超限时在一个设计下拆多个任务，但 QA 又要求任务证明整个设计契约，拆分方法与验收单位发生冲突。当前收紧为一个有效 DESIGN 最多有一个有效设计任务；确认设计不会自动建任务。大型设计要重新检查模块边界，不能依赖不断细分任务来规避完整契约的验收。未领取任务可编辑，领取后锁定；CR 来源任务需要修正契约时，在 `needs_revision` 中处理。

### Feature 为什么没有一并合入 Design

最初 REQ 按关注点拆需求，TASK 按可交付物拆工作，却被近乎一对一绑定，横切关注点因此难以成为可实施任务。第一步实际加入了一个 DESIGN 覆盖多个 REQ 的关系，并决定复用 DESIGN 作为功能单位，不新增 Feature。但“设计还没出现，范围、负责人和开发顺序已经需要确定”是独立需求；同一个功能内也可能有多个模块设计。因此 Feature 保留为计划、归属和开发顺序的单位，DESIGN 负责模块方案、契约、验收及选择理由。

当前主流程是 `INPUT → 项目规范 → FEATURE → DESIGN → TASK`。这表示工作顺序，并非逐层外键链：INPUT、项目规范和 Feature 属于项目，DESIGN 属于 Feature，设计任务关联 DESIGN。Feature 不另设确认状态机，设计进度由其有效设计派生，避免再维护一套会与设计冲突的状态。

<a id="dependencies"></a>

### 依赖关系从多层复制改为各自表达顺序

原来 REQ、Feature、Draft、Task 都维护依赖，生成下游对象时复制关系；上游再编辑后，各层容易分叉。于是先收敛为 Feature 的无环依赖图。后来出现无需新建 DESIGN 的 CR 来源任务，又增加显式 TaskDependency，以表达具体任务间的执行前提。

这次补回任务依赖有不同的职责：Feature 依赖表达功能开发顺序，TaskDependency 表达任务之间的额外顺序，后者不再是前者的复制缓存。两者都不代表运行时调用图。领取时检查显式任务依赖与 Feature 的传递上游，后续放行也检查相关上游条件；可领取提示在读取时派生，避免保存一份容易过期的阻塞状态。

方法上也有一次纠偏：先把功能边界与排队顺序分轮讨论，避免为了依赖图整齐而按技术层切功能；随后把检查重点从“删掉多余依赖”转向“找出缺少的前提”。多一条依赖会延迟开工，漏一条却可能让任务依照尚不存在的契约开发，两者代价不同。后来服务端检查从直接上游扩展到传递上游，防止深层前提被重开后，下游仍被误判为可领取。

Feature 设计全部确认，只表示设计工作已完成。开发完成还要求有效设计有对应任务，且所有有效任务完成；没有设计或任务不能被当成完成。这一差别保留了计划、设计和交付各自的含义。

## 3. 设计深化：删掉需求条目后，怎样避免遗漏

### 全局约束与局部方案需要不同位置

去掉独立 REQ 层没有消除需求澄清责任，也没有让每份设计自行决定全部工程约束。项目规范承接从已讨论材料中整理出的全局决定，包括固定栈、质量线、界面约定和非功能基线。规范是项目单例，确认后供后续设计遵守；性能等全局性质留在规范里，不为每条约束制造一个开发任务。

项目规范最初加入时，具体症状是技术栈在各条 REQ 中重复、性能约束被迫生成独立设计、质量线与项目边界没有统一位置。它被安排在需求讨论之后，是因为之前信息不足；职责是汇总、去重、提升为项目约束并确认，不是再建一套多轮需求分析。项目单例也不发独立业务编号。

术语问题又与规范不同。词义会在澄清和设计中不断补充，若每补一个词都重开规范，会增加不必要的审批。因此术语表独立维护、不设确认门，规划上下文携带术语，下游也能只读查询。这样做是因为模型可能并不知道自己已经误解某个词，不能只靠它主动检索。当前尚未为此引入 RAG。

当时不把术语表放入规范，还有一个更强的原因：规范重开会级联标记下游设计，频繁补词将触发整批复审。这条级联后来删除，但术语高频维护与规范确认的差别仍在。术语表保留用户原词、用于代码命名的英文名和禁用表达；解释只存一份，避免双语解释各自演化，术语本身是项目内标识，也不另发编号。这里不做按相似度检索，是因为模型不知道哪个词已经用错，禁用表达需要随上下文可见。

<a id="boundaries"></a>

### 从任务中的骨架，转向先确定基础设计和模块契约

早期曾把架构当成“第一个任务顺手搭的骨架”，关键决定容易做得晚、散落在局部实现里。后来把架构基础与界面基础明确为 Feature 的一种职责：前者确定横切策略、持久化、运行拓扑和扩展契约；有界面的项目再由后者统一 Design System、App Shell 和共享交互。它们沿用 Feature/DESIGN，不增加另一套规划实体。

这并不要求提前建设庞大框架。基础设计应支持能验证主要连接的最小可运行骨架，顺序由真实构建前提决定。功能边界依据独立变化的决定、信息隐藏和限界上下文划分，不能按处理步骤或 model/service/view 层机械切割。基础能力与用户功能、核心与通用子域是判断后的标签，不是切分算法；成熟通用能力优先复用，高风险核心能力尽早验证。

设计内容也从部件名称和简短职责，推进到可检查的契约：对外操作、输入输出、前后置条件、失败行为和调用关系。只要求模块实际拥有的接口和持久化，不给纯界面模块硬造数据表；内部函数组织和文件布局仍由实现者决定。

这还修正了两种相反的偏差：早期把 Feature 只定义为用户价值切片，导致没有直接功能需求对应的共享基础与技术核心无处归属；后来不能又因为引入 foundation 标签，就规定所有项目必须有同样的技术部件。边界由项目的真实职责决定，标签描述边界，不能代替分析。

承重技术选择也不能全部推给 coder。影响模块边界、依赖方向、持久化模型或运行拓扑的决定，应在设计中点名并解释取舍；项目内各模块共同遵守的选择回写规范。曾把“规范里没写”理解成“可以不决定”，也把这些要求放在已有功能地图时会跳过的轮次中。后来改为常驻原则，并用明确产物承载接口与决定，避免规则虽然下发、实际执行路径却绕过。

<a id="methods"></a>

### 从规定形式，转向让设计决定可以被检查

早期要求设计至少给两个方案，但可能只得到一个真实方案和一个陪衬。当前默认给有依据的推荐，只在存在实际分歧时比较备选。同样，抽象地宣布“需求已经问全”不够；阶段方法要求把原始要求映射为结构决定，呈现草稿、契约和验收，再围绕影响边界与行为的选择澄清。

技术上重要而用户缺乏判断依据的问题，由 agent 提出推荐及理由，供人纠正；不把所有工程决定都变成问卷。曾借鉴 superpowers 的选择题、有界自检和全局约束下发，但没有引入另一套文件式 spec/plan 实体，也没有照搬已删除 REQ 阶段的流程。

把需求并入设计后，也曾在实施中再次拆出“只谈需求、不写方案”的草稿轮，并叠加行为配额和深度分档，结果基础设计只剩细节追问，无法作出结构决定。随后撤回这些平行规则，让草稿就是设计本体，需求理解与实现方案同轮分栏呈现；审查时把目标、验收、约束、边界和失败模式作为对草稿的检查维度。这样人可以单独否定需求理解或方案，不必再把两者串成两套审批流程。

后来需求内容又从 `design_scope` 中抽成 `mined_requirements`，因为埋在方案散文里的需求既容易写薄，也无法汇总。需求汇总页从设计派生、不存第二份内容，并保留用户原要求与设计时补充内容的来源区别。字段独立是为了可见和可汇总，不是把 REQ 实体和流程加回来。已确认设计缺少需求记录会被点名，但没有单凭该字段非空新增确认门：一行填充文字不能证明需求完整；尚在编辑的草稿也不与已确认缺失混在一起告警。

方法按当前阶段下发，并独立于 HTTP 路由维护，以控制上下文和维护成本。通用提示词只写机制与判据，不能把某次测试项目中的实体写成所有项目的必做项；示例需要避开当前测试项目，并分散领域。方法是否有效要看产物和行为，不能因为文字变长、要求变多就认定质量提高。

这一收缩有具体依据：旧 `project_context` 同时下发全部阶段方法和当前阶段方法，当前内容重复、其他阶段又占据注意力；改为只发 `active_stage_method`。随后把方法文本从路由模块拆出，并删除系统提示词里的方法镜像。MCP 与 OpenAPI 的契约说明则保留，因为它们服务互相读不到对方声明的客户端；不能把必要的接口语义也当成重复方法删掉。

## 4. 变更治理：上游改了，下游是否必须重做

### 从级联状态，拆成成熟度、依据和变更决定

状态简化先于 `needs_review` 的删除。第一轮把各实体分散的状态收敛为共享四态生命周期，减少大量无人使用的状态与 PR/CI 镜像；当时仍把“已确认但上游变过”存成 `needs_review` 并沿关系传播。

随后发现，内容自己的成熟度与依据是否过时被写进了同一个状态。级联还要决定传播到哪层、谁来解除、是否打断已开始的开发。于是再从四态收敛为三态，把上游变化移出内容状态。

调整后把三个问题分开处理：

| 要回答的问题 | 当前机制 | 为什么分开 |
| --- | --- | --- |
| 内容是否已经确认 | `draft / needs_clarification / confirmed` 生命周期 | 确认后锁定，修改先重开，状态只表达自身成熟度 |
| 当前内容依据的上游是否变了 | 版本快照与 suspect 提示 | 上游变化不必然推翻下游，需要判断实际影响 |
| 为什么改、谁批准、是否已应用 | ChangeRequest | 记录变更决定，避免用状态变化代替原因和批准 |

删除另作软删除维度，不再用 `cancelled` 混入成熟度。版本快照支持追溯与恢复。当前 suspect 对比 FEATURE → DESIGN → TASK 的依据版本；上游删除或缺失也会提示，项目规范不再级联改写下游状态。

规范退出级联是单独作出的决定：设计在规范约束下形成，但并非由规范内容直接派生，普通规范修订不应把所有设计自动打回；根本性的栈或边界变化仍需人工复审。suspect 选择记录上游版本号，而不是比较一般更新时间，避免并发编辑和无关更新混淆依据。Feature 也补了版本历史，但不因此新增确认生命周期。

suspect 不自动阻塞或重开对象。检查后若内容仍成立，就对齐依据；需要修改则编辑并重新确认。这样把“发现变化”交给系统，把“变化是否使原方案失效”留给判断者。

### 从批准记录，补到可检查的应用与反向追溯

CR 最初存在“记录已应用，却没有检查目标实际改过”的缺口，设计和任务也不容易反查改写它们的原因。后来加入建单时的目标版本快照与详情中的关联 CR：可版本化目标全部未改时拒绝应用，部分未改会报告；无法取得版本的目标不冒充已验证。

CR 仍不自动改写目标，实际内容经正常编辑接口更新。版本变化只能证明内容动过，不能证明改得合理；反向关联用来解释原因，不复制第二份规格。这是当前验证能达到的边界。

CR 还从单目标扩展为多目标，因为只登记一个目标会让同次变更涉及的其他设计及其任务漏出影响分析；支持任务作为目标，则是为了表达设计规格不变、已交付代码需要修改的情况。已完成任务对齐新依据时要求理由并留痕，因为这时断言的是“交付代码仍满足新依据”，不再只是修改一段未交付的说明。另一次排查发现 CR 虽有模型与工具，却未进入项目上下文和阶段路由；补上可达性后，变更流程才真正能被 agent 走到。

### 已交付后的新工作，不再强迫重走原设计任务

新需求与原验收不满足需要不同处理。把所有后续工作都塞回原任务，会把新范围倒算成旧交付失败；为每个变更再建一份 DESIGN，又可能只是制造对象来满足流程。

当前已交付工作的新增或变更默认经获批 CR 创建或归入来源任务。来源任务直接属于 Feature，不要求新建 DESIGN；一个任务可关联多个获批 CR，一个 CR 只归属一个任务。只有确认原交付本身未满足原设计，才重开已完成任务。普通交付验证中的修复与这类契约变更如何区分，见[交付验证](#delivery)。

## 5. 开发执行：怎样交接上下文并判断任务完成

### 从更多角色和上下文副本，改为按职责读取来源

下游原来区分 tester 与 reviewer，后来合为 qa：实现由 coder 完成，qa 独立测试并检查设计符合度、范围和边界，manager 对人沟通、协调并根据证据裁决。减少角色数量是为了减少重复交接；独立检查依靠检查者与实现者分离。

曾有 DevelopmentInstruction 和 TaskPackage，把任务、设计、规范再次持久化，并要求额外生成。它们没有独有信息，却可能缺失或过期，因此删除这些副本。当前任务读取直接附带绑定契约与已确认规范，其他背景通过只读工具获取；项目模板也从项目和规范即时派生。全局关键约束随任务推送，减少忘记查询和中间转述丢失。

这里不仅是减少存储。旧流程曾出现代码已经完成、任务包仍未生成、系统状态还停在已领取的故障；删除物化副本时曾先向子代理开放全部只读工具，之后又收窄为任务范围，避免项目级长上下文。只开放查询仍会遗漏主动读取，所以设计正文、已确认规范逐步改为随任务原样返回；缺失时明确返回空值，而不是用摘要或默默省略来掩盖。

上下文按职责控制：manager 在 Planning/Delivery 与 Build 模式间切换，规划或交付时再读取项目级上下文；coder 和 qa 只获得任务及指定来源、设计、规范和术语等只读工具。工具层区分读写，比在一个多动作工具的说明里写“只许读取”更明确。但这是模板授予的工具范围，不等于隔离了 agent 经 shell 访问服务的所有途径。

### 开发前评审为何保留，又为何改变形式

预审最初只能从界面操作，manager 的业务编号工具没有对应动作；模板又从领取直接跳到派 coder，实际形成“要评审却没有入口”的断链。于是把预审暴露给 manager，让人可在对话里决定、manager 记录，界面按钮保留。代价是服务端验证状态与认证身份，不能独立证明对话中的批准；当前是否需要新增人工批准，由模板结合任务与既有授权判断。

预审也曾退化为复述设计后再问一次同意。后来把两道检查的职责分开：设计确认检查规格自身是否一致、验收是否能在本设计与声明上游内证明；领取后的预审核对真实仓库是否满足设计假设与上游承诺。预审应交出带路径、符号或命令结果的差异事实，再提出处置建议，不能把“上游没交付”悄悄改写成“本任务顺手补”。

之后又补查方案义务与验收之间的空隙：设计明确要求某机制时，仅有行为相同的测试可能放过更弱实现，需要指出哪个承诺尚无判据区分，而不是任意扩展设计。`start_pre_review` 后来降为可选的进度标记，允许从已领取状态直接记录判定，避免为了按钮顺序再增加无独立信息的步骤。

<a id="quality"></a>

### 从平台与 CI 状态，回到任务自己的完成证据

早期实现把托管平台和 CI 查询纳入任务推进，后来删除平台客户端与轮询；自动合并属于同时放弃的早期设想，不应写成已经实现后再删除的能力。除了适配成本，还有完成条件的问题：开发初期 CI 可能尚未建立，不能要求首个任务先满足不存在的基础设施。

当前任务通过领取、适用预审、编码、qa 和 PR 阶段推进。coder/qa 结果及逐项验收证据用于放行，仓库操作由 agent 执行，合并由人在托管平台确认后上报。`completed` 表示检查通过且已记录关联 PR 合并，不代表 Harnoq 亲自构建代码或验证远端 CI。CI 由项目自行负责，跨模块和系统验证另有交付阶段。

这也是分两步收缩的：先删除逐任务 CI 门，仍查询 PR 是否合并；随后真实的自托管仓库因只支持 GitHub provider 而无法关联 PR，才连平台适配与轮询一起删除，保留 agent 已能执行的仓库操作和 Harnoq 的事实记录。

任务执行状态也简化过。`coding / agent_qa / fixing` 原本追踪同一 manager 会话内的往返，轮次实际已在 AgentRun 中记录，因此合并为 `in_progress`。预审镜像字段、缓存的质量结论以及没有任何观察者写入的运行中/分支创建等状态也被删除。关键顺序改在放行处验证：最新 coder 与 qa 都通过，且 qa 晚于 coder，防止旧评审为后来代码背书。

重开任务又暴露了“最新 PR 不等于本次 PR”：旧的已合并 PR 曾让返工未交付就被记为完成，也曾阻止本轮撤回。于是按当前领取划分执行尝试，完成和合并检查只认本次关联的 PR，旧记录保留作历史，不能复用作新交付证据。

### QA 结果从一句结论变为可核对的证据

曾有 qa 因工具不可达拿不到设计，却只能借用失败状态，导致 coder 被派去修复一个根本没有作出的判断。因此引入 `blocked` 表示未能验证，与 `needs_fix` 区分；放行读取最新结果，不能沿用阻塞之前的通过。

随后要求逐条引用验收标准、给出判定与证据，并记录实际测试命令、退出码和测试数量。`deviates` 表达“代码能工作但偏离约定”，不能混入通过；绿套件也不能替代产品实际路径的证据。后续又派生 `cleared_failures`，提示失败是被真正解决，还是因判据删除或在仍缺测试的情况下改判而消失。它用于留痕与人工判断，不强制新增测试数量，否则只会鼓励为了过门造测试。

<a id="evidence"></a>

### 从减少验收的怀疑，转向降低重新找证据的成本

复盘曾怀疑代码量与验收判据过多，但重新计量发现，大量行数来自规范明确要求的文档字符串与注释，主要功能也来自原始需求，不能归因为 agent 任意扩张。判据数量是否过多同样没有充分证据，限制条数、超量解释和减少验收等建议随之撤回。能确认的问题是重复机制与从头定位证据的成本，分别交给集成收敛和证据复用处理。

当前记录结构化 QA evidence，任务读取提供历史证据索引和零测试覆盖提示。旧证据帮助定位，不继承旧结论；QA 仍从当前产品实际路径验证完整契约。新包装层可能改变行为，因此旧文件未改、测试套件全绿、判据未变或文件交集，都不能单独替代复验。

昂贵测量先估数量级并报告代价，QA 同时说明价值与成本；取舍交给有权决策的人，不自动删测试。lint 等局部检查留在开发任务内，NFR 则区分已承诺的 `commitment` 与方向性的 `direction`（兼容 aspiration 等写法），避免把愿望直接变成强制交付门。

这项取舍也经历过更正：当时曾把“缺少一项性能优化”认定为“承诺没有兑现”，重新核对后发现真实产品路径已满足目标，额外优化不是失败修复。没有采纳再加估算字段、风险档和审批层的重方案，而把数量级估算放到 coder、测试信息价值放到 qa。慢但保护真实风险的测试仍有价值，“昂贵”本身不能成为扣分或删除覆盖的理由。

另一条“提示词已送达但模型没有照做”的归因也被撤回：下游实际运行的是旧配置文件，相关新规则根本没送到。Planning 方法随请求更新，Build 模板却是下载后落在仓库的生成物，不能当作活引用。刷新工具保留开发者本地模型选择、更新生成文案，指纹帮助辨认版本；诊断先检查实际送达的配置，再讨论模型行为。该次观察本身不支持把故障归为模型不遵守规则。

## 6. 交付验证：为什么任务全部完成还不够

### 模块验收留下了无人负责的整体问题

分模块设计和开发减少了每个 agent 的上下文，但也带来局部视角。任务各自通过后，仍可能没有真实生产入口、跨模块接缝没有接通，或多个模块重复承担同一职责。这些问题往往没有天然的单个 DESIGN 所有者，不能要求某个 coder 靠局部任务顺便解决。

因此显式补上 Integration 与 System：Integration 检查装配、模块接缝和职责收敛；System 从用户视角检查完整旅程与非功能承诺。新增的是整体交付责任，不能用“所有开发任务完成”代替。

首次复盘的触发事实是任务和 PR 已全部完成，但生产入口仍未接上，各模块自己的检查却真实通过。最初决定把“补装配”和“行为不变的收敛”分开，先能运行，再清理共性；后来两类义务归入 Integration，System 则承担用户旅程与 NFR。曾讨论在每次设计确认前检查全项目重复操作、预设横切所有者，但没有采纳：当时选择接受局部上下文带来的重复成本，再集中收敛，而不是要求每个 coder/设计者掌握全部项目。

交付清单本身也不是一开始就有。早期曾把“不建测试用例/mock 实体”误扩成“不新增任何实体”，让阶段只有方法、没有可见的待验证义务。后来明确纠正：判据能验证，不等于阶段状态有承载位置，于是加入 INTEG/SYS 事项和独立页面。

### 验证工作经历了从任务化到执行轮次的调整

早期交付方案沿用设计与任务流程，为验证切片建立 DESIGN、TASK，再经过 Build。随后改为直接用来源任务承接集成工作，去掉额外设计。继续调整时又把集成和系统工作移到交付执行轮次，取消交付任务流；期间曾重新尝试把集成发现批量归入修复任务，最终也移除，统一在轮次中直接记录验证与普通修复。

这些反复的关键区别是：验证义务、一次执行和新增开发范围不是同一个对象。若每次验证或普通修复都必须先建任务，会把推进流程所需的操作变成新的交付负担，还需要同步任务与清单的完成状态。

当前分别承载：

| 对象 | 记录什么 | 为什么独立存在 |
| --- | --- | --- |
| INTEG / SYS | 必须验证的义务、来源与覆盖情况 | 清楚知道还欠哪项验证，不把矩阵每行都当待办 |
| RUN | 本轮代码/设计基线、执行证据、修复、资源和阻塞 | 同一义务可能反复验证，需要区分每轮结果 |
| CR 来源 TASK | 经批准的设计或契约变更所需执行工作 | 新范围需要独立批准与交付，普通复验不必走同样流程 |

普通 Integration/System 验证和修复直接留在事项与 RUN；设计或契约变更走 CR，必要时创建或复用来源任务。当前来源任务只接受获批 CR，不接受直接用 INTEG/SYS 建任务。技术盘点由 agent 执行，产品取舍、豁免、显著额外成本或外部资源、破坏性操作及无法消除的需求歧义，仍需人作决定。

### 从“有测试名称”，推进到“当前版本有执行证据”

交付盘点也逐渐明确了证据边界。Integration 先证明实际生产入口，再沿已接线边检查部件可达性，核对有方向的 producer → consumer 接缝，最后分析重复职责。构建成功不是生产可达；代码或名称相似也不足以判定重复，需要比较契约、调用语义和所有权。收敛必须保留调用者行为，并以结构测试防止复发。

System 从 INPUT 的用户场景和规范中的 NFR commitment 盘点，选择能重跑的产品边界验证。组件测试不能冒充完整旅程，资源不足应记录阻塞，不能以 mock 或“缺失时能报错”证明真实资源成功。

在这之前，NFR 只有规范中的声明，没有明确验证归属。后来增加设计的 `verifies_nfr` 和派生覆盖视图，暴露“无人认领的承诺”与“对不上规范的认领”；按规范中的指标字面匹配，避免模糊匹配产生假覆盖。字段存在却普遍为空时，又要求有 commitment 的项目在设计确认时明确回答，方向性要求不强制制造认领。模块认领负责局部实现与测量，System 仍须在产品边界核对承诺，二者不能互相冒充。

早期用任务或测试名称填写覆盖关系，或只比较最后一个任务完成时间，都不足以证明本轮通过；尤其没有新任务的重入复验，没有可用的新任务时间戳。当前覆盖证据绑定执行轮次和代码版本，阶段关闭结合真实完成事件、基线指纹、清单审计、资源条件和轮次检查。事项可以有理由地豁免，但清单数量归零本身不等于交付通过。

基线时间后来改为读取 TaskEvent 中真正转入完成的事件，避免一次负责人更新或依据对齐被误认为新交付。清单校验通过只说明结构有效，最终完成审计另行检查当前义务和证据；零缺口、零新任务的复验也能产生真实完成记录，无需造任务或 PR 推进时间戳。新交付或相关设计、事项变化会使旧审计失效，并要求先恢复 Integration，再继续 System。

为减少重入时从头拼清单，后来支持取回保存的完整盘点并增量修订，但使用读取版本令牌拒绝过期修改；基线变化仍要补当前运行证据，不能把旧材料直接盖成新结论。外部资源则分别验证“资源就绪”和“产品路径真实调用成功”，不能用目录存在、健康检查或测试替身替代后者。授权豁免可以跨阶段记录，是为解除“修复等豁免、豁免又等修复完成”的循环；它仍不能自动完成任务或关闭阶段。

Integration/System 因而有独立列表页和执行轮次，不挤进单份设计详情。精确字段及重入规则见 [API：交付验证与完成审计](api.md#delivery-audit)。

## 7. 工程支撑：身份与数据怎样跟上流程变化

### 从填写负责人，走向认证身份和归属历史

早期负责人是自由文本，预审人还曾默认使用认领人。这无法可靠区分同名用户，也不能表达谁在何时承担工作。后来加入账号、JWT、网页写操作的 CSRF 校验和可撤销的个人 API 凭证，负责人关联用户，旧文本通过显式关联补齐。

归属变更与内容版本分别记录：开发前转交需要重新领取及适用预审，开发中转交保留既有工作，历史完成统计按当时负责人归属，不随当前负责人改写。状态流转时间也不冒充实际工时。

这解决了身份来源与工作留痕，但没有建立完整的项目隔离。当前登录用户协作访问同一组项目，管理员维护用户和分配，成员受工作归属约束；认证身份也不等于独立的人类同意证据。无认证的内部或测试路径仍存在旧字段回退。

<a id="storage-ui"></a>

### 从重放历史迁移，转向按当前模型建表

对象模型多次删改后，历史增量迁移链大量工作变成“先创建后来已删除的实体”，还可能因旧脚本导入当前模型失效。项目采用重建数据库的开发方式时，维护这条链收益有限，因此移除原迁移系统，由当前模型创建缺失表。

这个选择有明确条件：`create-schema` 不会升级已有表的列。后来为多来源任务提供显式副本重建工具，只读源库、在副本上转换，并先检查清理计划。它解决特定结构转换，不是恢复了通用增量迁移框架；今后结构变化仍需单独评估，历史清理计划也不能套用到任意项目。

数据库运行配置也按用途区分过：一次测试耗时排查确认，大部分时间花在一次性测试库反复建表的磁盘同步，而非业务计算。于是只对可丢弃的测试库放松持久化设置，生产使用 WAL 改善网页并发读写。这个决定有具体适用环境，不能把测试提速方式照搬到生产。

编号与数据库关系同样分清职责：用户和 AI 用业务编号识别对象，数据库外键及内部 service/repo 调用继续用原始 id；编号按项目分配且不因删除复用。没有必要为了展示一致性重写内部所有路由和 payload。

编号最初按实体类型全局递增，后来改为项目内独立计数；再把项目前缀并入生成并存储的完整编号，消除列表裸编号、详情拼全称的两种表示。分隔符选连字符而非斜杠，是因为业务编号直接用在 URL 路径段。对外引用统一，并不意味着内部数据库关系也改用字符串编号。

界面的稳定约定是列表入口、添加/编辑弹窗、删除确认和 Markdown 展示。这些是贯穿对象变化的交互规则，避免每个实体形成不同的操作习惯。

关系图也曾从手写 SVG 排布改为 Mermaid 自动布局，并把归属链与 Feature 依赖图分开表达。这样不再为每次对象变化维护一套交叉消除和层次布局算法，也避免把“属于谁”与“等谁完成”画成同一种关系。

### 接入从本地进程，走向共享服务

最初 MCP 通过 stdio 由每个客户端本地启动，意味着每个开发者都要 checkout Harnoq 并维护运行环境，与“多人使用一个共享网站”的场景不符。后来改为远程 HTTP，先单独进程和端口，再与 Web/API 合并到一个进程、同一端口的 `/mcp`。同进程部署还曾因同步 HTTP 调用自身阻塞事件循环，改为进程内转发到同一业务服务；远程独立运行仍可走 HTTP。

下游配置因此只需要服务地址，Harnoq 生成配置包，仓库初始化及 git 操作由客户端负责。后来又把 manager、coder、qa 的工作位置统一为当前项目目录：manager 建立或复用分支、传递准确路径，子代理在同一份工作代码上实现和验证，减少目录与分支不一致造成的交接问题。

### 实体重构为何必须检查完整调用链

首次删除 REQ 的施工曾只改对模型与服务，skill/MCP 还在导入旧对象，外部调用仍然失败；同次实施还误删了大量本应重写的测试，让绿色结果掩盖了断链。后来补回并改写测试，逐层检查页面、API、skill、MCP 与工具描述。CR 未进入阶段路由也暴露过相同问题：对象和动作存在，不代表使用路径真正可达。这里保留的是跨层核验的理由，不把那次施工用的测试数量下限变成永久质量规则。

### 通用写入去重为何被删除

早期 skill 层没有稳定的请求身份，却用请求内容哈希补出幂等键。相同参数既可能是重试，也可能是用户再次执行合法动作；它曾吞掉同一 Feature 下第二次创建设计、重开后的再次确认、恢复后的再次删除，并返回旧成功结果。

随后删除通用去重与成功回放，每次写操作重新执行，重复动作是否合法由领域服务检查，SkillInvocation 只留审计。接受的代价是重复追加内容等动作不会自动去重；这比在无法识别请求身份时静默漏写更可见。

<a id="limits"></a>

## 8. 当前取舍与仍未证明的部分

沿上述演进，当前设计保留了几条相互制约的原则。一个实体应有独立的信息或决策职责，否则优先从来源读取，而不是复制一份。一个状态应表达明确含义，成熟度、依据过时、批准和删除不混成同一状态。局部执行可以限制上下文，但必须由明确的交付阶段补足整体检查。减少中间步骤的同时，不能把真实的需求澄清、契约验收或人工决策责任删掉。

这些原则解释了为什么删除 REQ、PLAN、DRAFT 和任务包，却保留 INPUT、规范、Feature、Design 与 Task，又增加 CR、交付事项和 RUN。设计目标不是让对象越少越好，而是让每一份必须维护的记录都能回答独立的问题。

历史未决问题中还有两项明确取舍：没有既有交付需保护时，不强迫廉价编辑创建 CR，因此版本差异未必保存独立的决策理由；事后补齐并确认设计，也不证明它经历过规定的思考过程。曾考虑用耗时等信号证明过程，但没有可靠依据，不能把这些仍待评估的问题写成已解决。

当前仍有几类不能由现有记录自动证明的事：

- 版本变了，不证明变更合理；状态合法，不证明人的批准真实存在。
- 任务证据与 PR 合并已记录，不证明 Harnoq 验证过远端事实，也不证明完整产品已通过交付验证。
- 模板带有指纹、生成物已经刷新，不证明模型确实按要求执行；还需要行为评测。
- 一次项目复盘能发现问题，但不足以证明跨领域、跨模型都有效，也不足以据此删掉通用验收责任。

语义一致性、决策留痕、过程证明、身份授权与跨模型效果仍需评估，见[规划中的待评估问题](phased_delivery_plan.md#open-questions)。本文解释已经作出的选择；未采纳设想和被替代实现不会因保留历史而重新成为开发任务。

正文说明术语形成的原因，本表供提示词、MCP 工具说明和 OpenAPI 描述查阅。数据库字段与业务编号保持现有命名，工具调用使用实际接口名；例如 `harnoq_design_case_*` 对应当前 DESIGN 能力，不能仅因命名较早就判为废弃接口。确实用于兼容的旧名称应在实现中明确标注。

| Module / 模块 | 一个 `DESIGN-*`，封装独立变化决策并暴露契约 | 用 Feature 代称模块 |
| Architecture Foundation / 架构基础 | 项目级架构、持久化、横切关注点和 walking skeleton | “横向地基”“平台底座” |
| UI Foundation / 界面基础 | Design System 与 App Shell | “界面基础块” |
| `foundation` / `vertical` | `orientation` 的枚举值；分别表示 platform layer / vertical slice | “横向 / 纵向”中文比喻 |
| dependency graph / 依赖图 | `FeatureDependency` 的有向无环图 | “依赖脊” |
| consumer analysis / 消费者分析 | 列出能力的消费者以判断共享边界 | “consumer-map forcing step” |
| required design checklist / 必备设计清单 | 设计阶段的显式完整性检查 | “REQUIRED-BLOCKS GATE” |
| requirement clarification / 需求澄清 | 通过对话补全目标、验收、约束、边界和失败模式 | “聊深聊透”“挖透” |
| consolidation / 汇总提炼 | 将已确认材料整理为项目规范 | “收割” |
| INTEG-* / 集成事项 | 集成盘点发现的一项独立义务：装配缺口、未满足接缝，或经证据确认需要收敛的重复职责；每项有明确来源、状态及执行轮次 | 把矩阵每一行都当成事项，或把不同义务按人员/修复方式合并 |
| SYS-* / 系统事项 | 系统阶段盘点的一项独立用户旅程或 NFR 承诺；每项有驱动方式、来源及执行轮次 | 把系统事项当作 DESIGN，或把多个场景压缩成一段报告 |
| source-backed TASK / 来源任务 | 由一个或多个获批 CR-* 直接归入的通用执行单元；来源通过显式 FK 关联，不从文本推断 | 为每个事项强制创建一个 TASK，或把来源写在 DESIGN 文本里 |
| explicit TASK dependency / 显式任务依赖 | TASK 与 TASK 之间的有向依赖；领取前检查依赖 TASK 是否 completed，并检测循环 | 依据事项 kind、创建顺序或隐藏阶段规则推断顺序 |
| integration inventory manifest / 集成盘点清单 | 集成 Round 1 的内部结构化证据、生产入口、部件、接缝、候选和拟建 INTEG 载荷；通过 Harnoq 校验门后由 Agent 创建绑定事项，在执行轮次中验证与记录修复 | 把内部 manifest 当成要求用户逐项审查的报告，或把校验误说成完全无状态 |
| production entry point / 生产入口 | 在预期运行环境中实际执行交付行为并到达可观察边界的根；构建配置只能帮助发现候选 | 把 build/bundle/compile/package/codegen/test/dev/preview 命令、孤立 bundle，或仅名为 `main`/`start`/`run` 的源码当成入口 |
| production-reachable / 生产可达 | 从已证明的生产入口出发、沿每条已接线边传递得到的可达性 | 位于不可达子树内但内部 import/route 正确就算可达 |
| `assembly` / 装配缺口 | 使一个或多个已声明部件无法进入生产路径的一条确切缺失 producer → consumer 边；全量部件仍进入矩阵，INTEG-* 按唯一缺失边计数 | 按受影响部件数量重复建项，或把不同缺失边合成一项 |
| assembly matrix / 装配矩阵 | 每个声明部件一行的全量可达性检查表，是证据而不是 INTEG-* 批次 | 只列缺口，或把每一行都创建为 INTEG-* |
| `seam` / 模块接缝 | 设计声明的一条有方向的 producer → consumer 邻接；所有声明都进入接缝图，但只有未接线或没有一个通过的测试直接驱动该 producer → consumer 时才创建 INTEG-* | 泛指任何代码关系，或将已接线且已直接验证的行也建成工作项 |
| seam graph / 接缝图 | 从所有已确认能力设计的 `design_scope` 机械提取的完整有向邻接图 | Agent 自由联想的模块关系 |
| `duplicate` / 重复实现 | 经骨架、行为和调用者分析确认，同一契约、调用语义和所有权下存在多份实现，且实现分叉会构成缺陷 | 仅因名称、函数体、字段或数据形状相同就要求收敛 |
| exact-name collision / 精确同名候选 | 完整标识符在两个以上模块中完全相同 | 共享前缀、后缀、基类或类别 |
| source skeleton / 源码骨架 | 类型、函数/方法签名和数据字段，不含实现体；结合调用者用于比较职责 | 全量源码正文或文件名清单 |
| convergence / 实现收敛 | 保持所有调用者行为的前提下合并已确认的重复职责，并留下结构测试防止复发 | 一般性的重构或代码清理 |
| `journey` / 用户旅程 | 没有单个设计天然拥有、需要从用户视角端到端驱动的有序场景 | 单个页面或独立操作 |
| `nfr` / NFR 承诺 | 必须在系统边界实际验证的项目规范 NFR commitment；在系统阶段归入 SYS-* | 从组件测试结果推断已经满足的 NFR |

标准术语优先采用通行的软件工程表达，并定义其在 Harnoq 内的含义，避免口语隐喻和临时缩写。阶段与来源关系见[对象简化](#objects)、[变更治理](#changes)与[交付验证](#delivery)，不在术语表重复流程规则。

## 附录 B. 方法来源与采用边界

以下保留影响设计的调研来源，不代表 Harnoq 完整实现或认证符合这些体系，也不是当前外部产品能力与价格比较。

- ISO/IEC/IEEE 29148:2018：需求的澄清、分析、规约、验证和管理；这些责任保留，不要求一一对应持久化实体。
- SAFe 的治理层级与 Enabler 思路：层次按独立治理职责区分，基础建设同样需要明确交付位置；没有照搬其完整层级。
- V-model 与追溯模型：验收要能关联设计和执行证据；当前关系范围以 API 和模型为准，不宣称完整需求追溯矩阵。
- OSLC Change Management 与 suspect-link 实践：变更请求和依据过时提示分离；Harnoq 没有实现 OSLC 协议。
- D. L. Parnas，*On the Criteria To Be Used in Decomposing Systems into Modules*（1972）、*Designing Software for Ease of Extension and Contraction*（1979），以及与 D. M. Clements 合著的 *A Rational Design Process: How and Why to Fake It*（1986）：信息隐藏、模块接口及 uses 关系。
- B. Meyer，*Object-Oriented Software Construction*：Design by Contract，把操作约束落实成前置、后置条件和不变量。
- L. Bass、P. Clements、R. Kazman，*Software Architecture in Practice*：架构显著需求和质量属性场景，用于区分真正影响结构的决定与普通配置细节。

原调研中的厂商功能、价格及“下一步应实现什么”属于当时背景，不保留为现行结论；如需重新选型，应重新验证。
