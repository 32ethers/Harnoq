## 早期规划（保留原条目，附实现核对）

## 目的

本文档用于确定系统的分阶段开发范围。

当前阶段不进入详细设计，不定义数据库字段、接口参数或具体技术实现。本文只回答三个问题：

1. 先开发什么。
2. 每一期做到什么程度。
3. 哪些内容应该延后，避免第一版范围失控。

## 总体原则

系统的核心目标是把 AI agent 放入可控的软件工程流程中，而不是追求全自动无人开发。

因此，前期开发应优先验证一条主线：

> 需求进入系统 -> 形成设计结论 -> 拆成任务 -> 人工认领和审核任务 -> AI agent 在约束下开发和自检 -> 提交 PR -> ~~Github CI 验证~~（已取消系统 CI 门禁：测试由 QA 执行并上报） -> merge -> 项目测试 -> 上线后的需求和 bug 回流

分阶段开发应遵循以下原则：

1. 先跑通闭环，再增强自动化。
2. 先保证任务级质量，再扩展到项目级质量。
3. 先沉淀关键设计原因，再建设完整知识库。
4. 先以人为中心约束 AI，再考虑更自动化的 agent 编排。
5. Github 已经擅长的事情不重复实现，例如代码托管、PR 和 CI/CD。

## 阶段划分

建议分为 4 期：

1. 第 1 期：跑通开发闭环 MVP。
2. 第 2 期：补齐项目级质量流程。
3. 第 3 期：知识沉淀与 AI 上下文增强。
4. 第 4 期：企业化与自动化增强。

## 第 1 期：跑通开发闭环 MVP

### 目标

验证系统是否能够约束 AI 完成一个真实开发任务。

这一期的成功标准不是功能完整，而是能稳定跑通从需求到 merge 的最小闭环。

### 主流程

第 1 期需要支持以下流程：

> 用户创建项目 -> 输入需求 -> 和 AI/人讨论后形成设计结论 -> 基于当前已确认设计拆任务 -> 设置 Feature 与显式任务依赖 -> 程序员认领任务 -> 程序员 review 任务 -> 如果任务不合理则打回调整 -> ~~系统生成 AI 开发说明~~（已替代：即时读取任务上下文） -> ~~manager 下发 task package~~（已替代：角色自取设计、任务和规范） -> coder agent 开发 -> ~~tester agent 和 reviewer agent 检查~~（已替代：合并为 qa 检查） -> 如果有问题则 manager 组织 coder agent 修改 -> 提交 pull request -> ~~Github CI 执行~~（已取消系统集成：CI 由项目自身负责） -> merge -> 任务完成

### 开发范围

第 1 期应包含：

1. 项目创建和项目列表。
2. 需求录入和需求状态管理。
3. 设计结论记录，重点记录设计方案和设计原因。
4. 任务拆分。
5. 任务依赖关系。（已实现：Feature 图与显式 TaskDependency 并存，领取时检查两类上游；不是生成时复制多套依赖。）
6. 任务认领。
7. 开发前人工 review，支持批准开发或打回任务。
8. ~~AI 开发说明生成。~~（已替代：独立开发指令只是任务、设计和规范的重复物化；改由任务读取接口即时提供上下文）
9. manager、coder agent、~~reviewer agent、tester agent~~（已替代：合并为 qa，减少重复交接，保留独立测试与评审） 的协作约束和执行结果记录。
10. ~~Github 项目关联。~~（已取消托管平台集成：Harnoq 不维护平台 API 客户端；仅保留项目 repo_url 文本记录）
11. pull request ~~创建~~（已取消服务端创建：人或 agent 用仓库工具创建 PR）或关联（已实现：记录 branch_name、pr_number、pr_url）。
12. ~~Github CI 状态读取。~~（已取消：不做 CI/CD 客户端或轮询；CI 也不作为逐任务完成门）
13. merge 后任务状态更新。（已实现手工记录：调用 mark_pr_merged 后再 mark_completed，不自动感知远端合并。）

### 关键概念

第 1 期需要明确以下概念，但不要求实现复杂版本：

1. 需求：用户输入的原始业务意图或 bug。
2. 设计结论：对需求讨论后的方案，以及为什么这样设计。
3. 任务：可以被程序员认领和交付的开发单元。
4. 任务依赖：任务之间的前后置关系。（已实现显式任务边，另保留 Feature 的传递上游检查。）
5. 开发前 review：程序员在正式开发前检查任务是否合理。
6. AI 开发说明：系统~~生成~~（已替代：不持久化独立说明，通过读取接口即时组合）给 coder agent 使用的任务上下文。
7. manager：唯一对用户沟通并负责收口上下文、~~分发任务包~~（已替代：持久化任务包无独有信息，角色直接读取任务与设计）和汇总结果的统筹角色。
8. agent 检查循环：manager、coder agent、~~reviewer agent、tester agent~~（已替代：检查角色合并为 qa）之间的修改和检查过程。
9. ~~Github PR/CI：正式工程质量门禁。~~（已替代：Harnoq 检查 coder/qa 结果、验收证据和手工记录的 PR 合并事实，不验证远端 CI）

### 明确不做

第 1 期不做：

1. 完整 RAG 系统。
2. 复杂组织和权限体系。
3. 全自动 agent 调度器。
4. 多模型资源池。
5. 完整系统测试平台。
6. 完整集成测试平台。
7. 复杂审批流。
8. 替代 Github 的代码管理能力。

### 验收标准

第 1 期完成时，应能演示：

1. 创建一个项目。
2. 输入一个需求。
3. 记录一个设计结论。
4. 创建多个执行任务并设置依赖。（已实现：一个有效 DESIGN 仅有一个设计任务，新增工作可建来源任务；任务之间可显式设置依赖。）
5. 程序员认领一个可开发任务。
6. 程序员在开发前 review 任务，能够批准或打回。
7. ~~系统生成一份 AI 开发说明。~~（已替代：任务详情直接附带设计和已确认规范，不再生成独立开发指令）
8. 记录 coder agent 的开发结果。
9. 记录 ~~reviewer agent 和 tester agent~~（已替代：两角色合并为 qa，检查结果记录在 AgentRun）的检查结果。
10. 检查失败时能回到 manager 编排后的 coder agent 修改。
11. 检查通过后能关联或~~创建 Github PR~~（已取消服务端创建：由人或 agent 在仓库侧操作，Harnoq 只记录）。
12. ~~系统能读取 Github CI 状态。~~（已取消：不接入或轮询 CI，验收改为检查任务级 QA 证据和 PR 合并记录）
13. PR merge 后任务进入完成状态。（已实现手工流程：上报合并后调用完成动作，不由远端事件自动触发。）

## 第 2 期：补齐项目级质量流程

### 目标

从单个任务闭环扩展到项目级交付闭环：验证产品装配、跨模块接缝、重复职责、用户旅程和非功能承诺，并让问题回到适当的修复或变更流程。

### 主流程

> 能力任务完成 → Integration 盘点、验证及审计 → System 旅程/NFR 验证 → 普通修复留在执行轮次；契约变更走 CR 与来源 TASK → 按当前基线重入验证

~~进入系统测试 → 进入集成测试~~（已替代：当前先 Integration 再 System，先验证产品装配，再验证用户结果。）

~~每个测试事项拆成小任务~~（已替代：INTEG/SYS 清单和 RUN 直接承载验证；确有开发工作才创建有显式来源的任务，不为每次复验增加设计、任务或 PR。）

### 开发范围

1. 项目阶段流转。（已实现：delivery_gate 推导 Integration/System 是否待执行，RUN 提供开始、更新、关闭和放弃；不靠修改 Project 的 active/archived 状态表达阶段。）
2. ~~系统测试任务管理。~~（已替代：SYS 用户旅程/NFR 清单和 System RUN 管理验证，不要求逐项建 TASK。）
3. ~~集成测试任务管理。~~（已替代：INTEG 装配/接缝/重复职责清单和 Integration RUN 管理验证，关闭前检查审计与当前证据。）
4. ~~测试用例管理。~~（部分替代、保留缺口：交付事项已记录验证义务、驱动和可执行证据；独立的可复用测试用例库及其版本管理尚未实现，是否仍需要单独产品化待评估。）
5. mock 环境任务。（已有 mock_env 类型；~~统一创建 mock 环境任务作为项目测试前置~~（已替代：按验证需要复用或准备环境；真实资源验证不能被 mock 通过代替）。）
6. mock 数据任务。（已有 mock_data 类型；~~统一创建 mock 数据任务~~（已替代：按验证需要准备，不为推进阶段机械建任务）。）
7. 测试执行结果记录。（已实现：任务 QA 保存 test_run/逐项证据；项目验证保存事项命令、退出码、输出、版本、轮次及完整清单审计。仍不等于独立用例库的执行历史。）
8. 测试失败后的缺陷回流。（已实现：普通修复留在 RUN 与事项；改变既定设计/契约走 CR，后续以来源任务落实；已有能力修复完成后重新检查 Integration/System。没有独立通用 bug 跟踪实体。）
9. bug 修复任务生成。（已实现：可创建 bug_fix 来源任务，明确引用获批 CR；~~失败后必须先补 DESIGN 再生成任务~~（已替代：来源任务直接绑定依据，不要求设计壳）。）
10. 需求变更重新进入需求流程。（已实现基础路径：requirement_change 输入、CR 多目标分析/批准、来源任务；不会自动替人决定产品范围。）

### 明确不做

不建设替代项目自身工具的复杂自动化测试平台，不接入 CI/CD 或代码托管客户端。Harnoq 检查上报证据的结构、来源和一致性，实际执行由 agent 或人完成。

### 验收标准与当前核对

1. ~~所有开发任务完成后进入系统测试阶段。~~（已替代：先进入 Integration，当前集成完成后才可开始 System；门禁与 RUN API 已实现。）
2. ~~创建系统测试任务和集成测试任务。~~（已替代：创建相应清单和执行轮次；有开发工作时使用来源任务。）
3. ~~测试任务可以关联测试用例。~~（部分替代：事项可关联来源任务并记录精确测试证据；独立用例实体与任务关联尚未实现，保留评估项。）
4. 测试失败可以形成修复记录或变更请求。（已实现人工/agent 驱动的事项修复与 CR 路径，不宣称所有失败都会自动转成 bug。）
5. bug 或修复需求可以重新进入开发流程。（已实现：来源 TASK 可绕过不必要的新 DESIGN；重新打开旧任务只用于原交付不满足原契约。）

已有验证见 [交付轮次](../../tests/test_delivery_stage_runs.py)、[系统清单](../../tests/test_system_inventory_validator.py)、[集成资源](../../tests/test_integration_resources.py)与[集成完成验收](../../tests/test_integration_completion_acceptance.py)。仍需在不同项目上观察实际流程效果，不能仅凭这些测试宣布所有未来项目都可交付。

## 第 3 期：知识沉淀与 AI 上下文增强

当前已有设计理由、版本历史、CR 反向查询、上下文下发及 API/MCP 查询。下列原目标中完整文档库、统一检索和 RAG 尚未全部实现，不能把整个三期当作从零开始。

### 目标

让系统从流程工具升级为项目知识库。

这一期的重点是解决长期项目中常见的问题：

> 项目运行时间长了之后，团队成员知道系统怎么做，却不知道当初为什么这么做。

### 开发范围

第 3 期应包含：

1. 设计决策库。
2. 设计原因的结构化记录。
3. 项目文档库。
4. 需求、设计、任务、PR、测试结果之间的追踪关系。
5. RAG 检索能力。
6. 生成 AI 开发说明时自动带入相关背景。
7. agent 通过 skill 或 API 查询项目知识。
8. 文档沉淀和更新流程。

### 关键价值

第 3 期的价值不只是提升 AI 效果，而是让项目知识持续沉淀。

系统应能够回答：

1. 某个功能最初来自哪个需求。
2. 某个设计为什么这样做。
3. 某个任务依赖哪些设计结论。
4. 某个 PR 解决了哪些任务。
5. 某次测试失败后来如何修复。

### 明确不做

第 3 期不追求让 RAG 替代结构化数据。

需求、设计、任务、PR、测试结果之间的核心关系仍应由系统结构化管理。RAG 主要用于检索背景知识、历史讨论和长文档。

### 验收标准

第 3 期完成时，应能演示：

1. 查询一个功能的需求来源和设计原因。
2. 查询一个任务相关的设计、文档和历史决策。
3. 生成 AI 开发说明时自动带入相关项目背景。
4. agent 能通过受控接口读取项目知识。

## 第 4 期：企业化与自动化增强

当前已有账号、JWT、负责人、分配、工作量及操作留痕；尚无项目成员隔离和完整企业治理。以下保留原目标，自动调度与资源池仍是可选设想。

### 目标

把系统从可用产品增强为企业级系统。

这一期重点处理团队规模、治理、权限、审计、自动化和可观测性问题。

### 开发范围

第 4 期应包含：

1. 多用户。
2. 多团队。
3. 角色和权限。
4. 审批流。
5. 审计日志。
6. 多 Github 项目支持。
7. agent 配置模板。
8. 不同模型能力适配。
9. 更强的质量门禁。
10. 指标看板。
11. 更自动化的 agent 编排。

### 可选扩展

第 4 期之后，可以考虑：

1. 多模型资源池。
2. 自动 agent 调度器。
3. task.step 级别的任务拆分。
4. 基于任务依赖和模型空闲状态的自动分配。
5. 看门狗机制，处理 agent 死循环或反复失败。

这些能力适合在系统已有稳定质量闭环之后再做，不应提前进入 MVP。

### 验收标准

第 4 期完成时，应能演示：

1. 不同角色的用户在同一个项目中协作。
2. 关键操作有审计记录。
3. 不同项目可以配置不同 Github 仓库和 agent 模板。
4. 管理员可以查看项目质量和交付指标。
5. 系统可以根据任务类型生成不同的 agent 执行建议。

## 总结

推荐的落地顺序是：

1. 第 1 期先证明任务级开发闭环成立。
2. 第 2 期补齐项目级测试和缺陷回流。
3. 第 3 期建设知识沉淀和 AI 上下文增强。
4. 第 4 期再做企业化治理和更强自动化。

第一期必须控制范围。

只要第 1 期能稳定跑通一个任务从需求到 merge 的闭环，就已经验证了系统最核心的假设：

> AI agent 不能自由发挥，而应该在需求、设计、任务、开发前 review、agent 检查、PR ~~和 CI~~（已取消系统 CI 门禁，保留 QA 证据和人工合并记录） 这些工程约束下工作。

## 待评估问题与能力边界

以下保留已有观察支持但尚未形成实施决定的问题，不是已批准的开发范围，也不据此新增阶段门禁。决策留痕与上下文效果可结合三期评估，身份和授权可结合四期评估；其余问题需先验证是否有可靠、成本合理的解决方式。已处理问题及其限制见[设计依据](design-evolution.md#limits)。

### 1. 单份设计内部的一致性

实测曾出现同一设计的新段落声明拥有某能力，旧“不拥有”清单仍排除该能力。CR 多目标追溯和版本比较只能证明对象发生过修改，不能证明文本内部没有冲突。设计确认的方法要求复核，但没有可靠的语义一致性硬检查；暂无已批准的新增机制。

### 2. 廉价编辑缺少独立的决策理由

没有既有交付需要保护时，编辑设计不应强迫创建 CR。代价是版本历史主要说明“改了什么”，未必单独记录为什么、谁认可了决定。原讨论倾向不增加治理流程，保留此取舍，出现新证据再评估。

### 3. 事后补设计不能等同于经过设计过程

历史实测出现很快创建并确认设计，随后验收已合并代码的情况。字段齐全和测试通过不证明设计经历了规定的思考过程；仅用耗时阈值也不可靠。事后补设计不必然错误，但流程保证应止于可核查的内容、状态和证据，不声称验证了思考过程。

### 4. 账号身份不等于独立的人类批准证明

认证请求中的预审人已取当前用户身份，避免调用方随意用 reviewer 字段冒充另一人。但持有该用户 API 凭证的 agent 仍以同一身份操作，系统不能据此证明用户在会话里明确批准过。无 actor 的内部/测试路径仍有 reviewer/assignee 回退；不能把“已有用户系统”表述为原风险彻底消失。

实现：[预审服务](../../app/services/development_task_service.py)、[身份认证](../../app/core/authentication.py)。

### 5. 跨模型、跨项目的行为效果

模板指纹、刷新工具和行为评测脚手架已经存在。它们改善“发到了什么”和可重复测量，不代表已有跨领域、跨模型的充分验证。历史单个测试项目中的现象只支持提出假设，不能把该领域实体写成通用提示词的强制要求。

依据：[模板刷新测试](../../tests/test_refresh_agent_config.py)、[Build 评测](evals/build/README.md)。
