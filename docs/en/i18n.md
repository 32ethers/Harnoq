# Internationalization maintenance

[中文](../cn/i18n.md) · [English](i18n.md)

## Language selection

The Web UI supports `zh` and `en`. A supported `?lang=` query takes precedence over the `harnoq_locale` cookie, with English as the default when neither is set. Browser `Accept-Language` does not change the default. Explicit choices persist for one year in an HttpOnly, SameSite=Lax cookie (Secure on HTTPS). The selector preserves the current path and query parameters. Preferences are per browser, not account-wide.

## Translation boundaries

`app/locales/en.json` is the shared catalog. Chinese source messages are keys. Jinja uses `_(message)`; JavaScript uses `uiText(message)` or tagged templates such as ``uiText`Created ${number}``` with a corresponding `{0}` placeholder in the catalog. The current catalog is embedded as safely escaped JSON before the deferred translation and application scripts. Python display text can use `gettext(message, *values)`.

Only explicitly marked interface messages are translated. There is no DOM-wide text replacement or automatic translation of project titles, requirements, design prose, evidence, credentials, or historical records. Business numbers, database IDs, enum values, route names, and payload contracts are unchanged. Stored historical notes retain their original language.

For new UI messages, add a complete English entry and preserve every numbered placeholder. Never concatenate untrusted values into HTML translation output; use text nodes. The few existing fixed option markup messages contain no user interpolation. Use complete sentences where possible; keep markup-owned fragments in their existing order.

## Agent language

Stage methods remain one authoritative policy, with a language rule for explanations and new project prose. English and Chinese requirement markers map to the same internal digest categories. The English OpenWebUI orientation prompt is `skills/openwebui-system-prompt.en.md`; the Chinese original remains in place because it is a runtime input, not ordinary documentation. Keep their tool/approval guidance aligned with the current stage method. The English configuration page displays the English prompt.

Changing the Web language does not retroactively translate a project or choose the language of a separately connected agent conversation. Ask that agent to write in the desired language. Native and English glossary terms remain authoritative.

## Documentation layout

The repository README is the English entry, with a Chinese link. Existing documentation lives under `docs/cn/`; English counterparts live under `docs/en/`; images are shared under `docs/assets/`. Module READMEs moved under each language's `skills/`, `mcp/`, and `evals/` directories. Runtime prompts, OpenAPI definitions, and the root `AGENTS.md` retain their operational locations.

When changing behavior, update both language editions and check local links and anchors. Preserve historical paths inside `git show` examples: they refer to old commits, not today's filesystem.

## Verification

```bash
uv run pytest tests/test_i18n.py tests/test_web.py tests/test_app_js_smoke.py tests/test_requirement_digest.py
```

The language tests cover preference precedence, invalid language handling, template rendering, interpolation, catalog completeness, domain-content preservation, deletion confirmation, English requirement parsing, and documentation links. Existing app/diagram smoke tests load the same translation runtime as the browser.
