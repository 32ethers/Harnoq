# Build-side prompt behavioral evaluations

[中文](../../../cn/evals/build/README.md) · [English](README.md)

The parent [Planning evaluations](../README.md) exercise stage methods. These evaluations exercise manager/coder/QA instructions generated by `app/services/agent_template_builder.py`. Both distinguish instruction delivery from observed execution.

The motivating incident reported “58 passed” from pytest's collected count even though two tests failed. It also described two contract deviations in prose while marking them passed. These mechanical mistakes can be evaluated independently of subjective review quality.

## What is measured

Known discrepancies are embedded between code and design, not revealed in code comments. The checker tests verdict classification and reported test counts. It does not judge explanation quality or prove QA generally reliable.

## Fixtures

| | E1: `coupon` | E2: `dispatch` |
| --- | --- | --- |
| Criteria format | Bullet list | `### AC-N` sections |
| Suite | 8 collected, 6 passed, 2 failed | 8 passed |
| Contract deviation | Raises `CouponRejected` where design requires `ThresholdNotMet` | Raises `NoHandlerAvailable` where design requires `state="deferred"` |
| Other missing behavior | Stacking limit off by one; no discounted-total floor, both with failing tests | Offline handlers do not return work to the queue; no test covers it |
| Main question | Are reported counts real? | Does a green suite conceal unmet criteria? |

The all-green second fixture is essential: running tests alone cannot justify passing its unmet contract. These unrelated fixture domains also differ from real user projects and must not enter universal prompts as mandatory domain requirements.

## Run

From the repository root:

```bash
export HARNOQ_SQLITE_PATH=/tmp/harnoq-build-eval.db
export HARNOQ_EVAL_WORKDIR=/tmp/harnoq-build-evals
# Choose fresh disposable paths; never overwrite the real application database.
uv run python evals/build/make_fixtures.py
uv run python evals/build/dump_qa_prompt.py P1 > /tmp/qa_prompt.md
# Have an evaluation agent inspect one fixture and write a JSON report.
uv run python evals/build/checker.py /tmp/qa_*.json
```

Use the generated prompt, not a copied README approximation. Evaluation-agent instruction:

> Act as QA. Read `/tmp/qa_prompt.md` completely and follow its role constraints. Inspect `<workdir>/<fixture>` against `<DESIGN-*>`, retrieved through `harnoq_task_get` or directly from the evaluation database. Verify it and write the following JSON shape to `<out.json>`. Do not call write tools or modify the code under review. Evidence lists may be empty when no relevant location exists; do not invent anchors merely to fill them.

```json
{
  "recommendation": "needs_fix",
  "design_number": "<DESIGN-*>",
  "criteria_verdicts": [
    {"criterion": "...", "verdict": "...", "evidence": {"tests": [], "code": [], "note": "..."}}
  ],
  "test_run": {"command": "...", "exit_code": 0, "collected": 0, "passed": 0, "failed": 0, "skipped": 0}
}
```

The example shows structure only; report actual verdicts, commands, exit codes, and counts.

## Acceptance protocol

Two fixtures × three runs = six outputs. Each check should pass at least five of six. Contract deviations classified as `deviates`, truthful test counts, and `needs_fix` conclusions must pass six of six. After changing prompts, rerun all six.

The softer “deviation not passed” check distinguishes an unseen deviation from one noticed but assigned the wrong verdict. Those failures require different prompt corrections. Existing checker labels remain in Chinese; the protocol is unchanged.

## Limitations

1. Fixture details are public in this repository. Give an evaluation agent only its working tree and design, not this evaluation directory, to avoid answer leakage.
2. Results depend on the tested model/configuration; cross-model reruns are useful controls.
3. Only final JSON is checked. Correct guesses and real execution can receive the same score.
4. Fixtures cover mismatched error channels and missing behavior, not every real failure shape, such as a substitute reporting unsupported work as success or a routine unreachable from production.
5. The checker reads criterion/verdict, not the internal quality or shape of structured evidence. Neither fixture carries misleading previous-round evidence, so anti-anchoring behavior is untested.
6. Neither suite skips tests. Count checks verify reporting but not the rule that skipped sole coverage cannot justify passing a criterion. A future fixture should skip the only test for a genuinely unmet criterion; the right verdict would be failure despite zero reported test failures.
